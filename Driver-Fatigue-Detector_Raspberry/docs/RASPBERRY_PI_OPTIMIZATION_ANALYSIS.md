# การวิเคราะห์และแนวทางปรับปรุงสำหรับ Raspberry Pi 4

> **สถานะ:** โปรเจกต์ปรับเป็นโหมด Headless แล้ว — ไม่แสดงวิดีโอ/landmark, ใช้เฉพาะ detector ที่ความละเอียด 320px, 10 FPS, ส่งเว็บและเล่นเสียงตามสถานะครบ

## สรุปปัญหา

เมื่อรันบน Raspberry Pi 4:
- **ภาพกระตุก** เพราะ CPU/GPU ต้องประมวลผลหลายอย่างพร้อมกัน
- **Detection ไม่ดี** เพราะเฟรมช้า/ข้ามเฟรม ทำให้การนับ consecutive frames (ง่วง/หาว) ไม่ตรง
- คุณ **ไม่สนใจการแสดงวิดีโอ** แต่ต้องการให้ **detection ถูกต้อง + เสียงแจ้งเตือน + ส่งสถานะไปเว็บ** ได้ครบ

---

## สาเหตุหลัก (จากโค้ดปัจจุบัน)

### 1. โหลดบน Pi สูงเกินไปใน loop เดียว

ใน `gui_update.py` ฟังก์ชัน `update_frame()` ถูกเรียกทุก **30ms** (~33 FPS) และในหนึ่งรอบทำครบทุกอย่าง:

| ขั้นตอน | ผลต่อ Pi |
|--------|----------|
| อ่านเฟรมจากกล้อง | ปกติ |
| **Resize เป็น width=800** | ใช้ CPU/หน่วยความจำ |
| **MediaPipe Face Mesh** (refine_landmarks=True) | **หนักมาก** บน Pi |
| วาด landmark 3 รอบ (ตา 2 + ปาก 1) | cv2.polylines |
| cv2.putText หลายจุด | เล็กน้อย |
| **แปลงเป็น PIL Image → ImageTk.PhotoImage** | ใช้ CPU/หน่วยความจำ |
| อัปเดต Label ใน Tkinter | block main thread |
| ส่ง backend (ผ่าน queue แล้ว) + เล่นเสียง | ถ้าทำใน thread เดียวอาจมี spike |

เมื่อ Pi ประมวลไม่ทัน 30ms → เฟรมสะสม → กระตุก และการนับ consecutive frames (เช่น 20 เฟรมง่วง) ผิดเพี้ยน เพราะเวลาไม่ตรงกับ “จริง”

### 2. ความละเอียดภาพที่ใช้กับ Detection

- กล้องตั้ง 640x480 (ใน `detector.py`)
- แต่ใน GUI resize เป็น **800** ก่อนส่งเข้า MediaPipe → ภาพใหญ่เกินความจำเป็นสำหรับแค่ตรวจจับใบหน้า/ตา/ปาก

### 3. MediaPipe ถูกตั้งค่า “หนัก” ใน GUI

ใน `gui_update.py` บรรทัด 51–53:

```python
face_mesh = mp_face_mesh.FaceMesh(static_image_mode=False, max_num_faces=1,
                                  refine_landmarks=True, ...)  # refine_landmarks=True ใช้ทรัพยากรมาก
```

`refine_landmarks=True` เหมาะกับ iris/lip detail แต่สำหรับแค่ EAR/MAR แล้วไม่จำเป็น และทำให้ Pi ช้าลง

---

## แนวทางแก้ไขที่แนะนำ (เรียงตามผลลัพธ์)

### แนวทางที่ 1: โหมด Headless / ลดการแสดงวิดีโอ (แนะนำมาก)

**แนวคิด:** ไม่แสดงวิดีโอเลย (หรือแสดงแค่สถานะ/ตัวเลข) เพื่อให้ CPU ไปโฟกัสที่ “อ่านเฟรม → ตรวจจับ → ส่งสถานะ/เสียง” เท่านั้น

- **ลดความละเอียดที่ใช้ใน detection:** อ่านเฟรมแล้ว **resize เป็น 320x240 หรือ 320x180** ก่อนส่งเข้า MediaPipe (ไม่ต้อง 800)
- **ลด FPS การตรวจจับ:** ไม่ต้องทำทุก 30ms อาจเป็น **5–10 FPS** (ทุก 100–200ms) ก็เพียงพอสำหรับการนับ “ง่วงต่อเนื่อง” และหาว
- **ปิดการวาดภาพบนจอ:** ไม่ resize สำหรับจอ, ไม่สร้าง PhotoImage, ไม่อัปเดต video Label → ลดการใช้ CPU/หน่วยความจำและลดการ block ของ Tkinter อย่างมาก
- **GUI แสดงแค่:** สถานะ (NORMAL / DROWSINESS / YAWN / CRITICAL), EAR, MAR, จำนวนเหตุการณ์, ปุ่ม Start/Stop
- **เสียงและเว็บ:** ยังใช้ logic เดิม (จาก `status_message`) ได้เหมือนเดิม เช่น `start_alarm_thread(status_message)`, `_send_periodic_backend(...)` — แค่ให้ค่าที่ได้มาจาก detection loop ที่รันสม่ำเสมอและไม่ถูกหน่วงด้วยการแสดงวิดีโอ

ผลลัพธ์: **Detection สมูธขึ้น, สถานะ/เสียง/ส่งเว็บถูกต้อง**, ภาพไม่กระตุกเพราะไม่มีการแสดงวิดีโอ

---

### แนวทางที่ 2: ลดขนาด Display (ถ้าต้องการเห็นภาพอยู่บ้าง)

ถ้าต้องการยังเห็นภาพจากกล้อง:

- **แสดงภาพขนาดเล็ก:** แสดงที่ **320x240 หรือ 256x192** แทน 800
- **ข้ามเฟรมสำหรับการแสดง:** เช่น อัปเดตภาพบนจอแค่ **ทุก 3–5 เฟรม** (แสดงที่ ~6–10 FPS) ขณะที่ **การตรวจจับยังทำที่ 5–10 FPS แยกกัน** (ดูแนวทาง 3)
- **ปิดการวาด landmark บนภาพ:** ไม่เรียก `draw_landmark_box` และ putText บน frame ที่ใช้แสดง จะช่วยลดงานบน Pi ได้

---

### แนวทางที่ 3: แยก “การตรวจจับ” กับ “การแสดงผล” (ดีสำหรับความสมูธ)

**แนวคิด:** ให้มี 2 ส่วนทำงานไม่ผูกกัน

- **Thread (หรือ process) สำหรับ Detection:**
  - อ่านเฟรมจากกล้องที่ความละเอียดต่ำ (320x240)
  - รัน MediaPipe ที่ **refine_landmarks=False**
  - คำนวณ EAR, MAR, head tilt ตามเดิม
  - อัปเดต **ตัวแปรร่วม (shared state)** เช่น `current_ear`, `current_mar`, `status_message`, flags ง่วง/หาว
  - เรียก **เสียง** และ **ส่ง backend** จาก thread นี้ (หรือส่งสถานะไปให้ main thread ทำก็ได้)
  - รันที่ **5–10 FPS** (เวลาคงที่ เช่น 100–200ms ต่อเฟรม)

- **Main thread (GUI):**
  - อ่านค่าจาก shared state แล้วอัปเดต Label (สถานะ, EAR, MAR, จำนวนเหตุการณ์)
  - **ถ้าต้องการแสดงวิดีโอ:** อ่านเฟรมอีกทางหรือรับจาก queue แล้วแสดงที่ขนาดเล็ก และข้ามเฟรม (เช่น อัปเดตทุก 200ms)
  - **ถ้าไม่สนใจวิดีโอ:** ไม่แสดงภาพ แค่ refresh ตัวเลข/สถานะทุก 100–200ms

ผลลัพธ์: **Detection รันที่อัตราคงที่ → นับ consecutive frames ถูกต้อง → สถานะ/เสียง/เว็บถูกต้อง** และถ้ามี display ก็ไม่ไปหน่วง detection

---

### แนวทางที่ 4: ปรับพารามิเตอร์ MediaPipe และกล้อง

- ใน `gui_update.py` ตั้ง **refine_landmarks=False** (หรือใช้ instance จาก `detector.py` ที่ตั้งไว้แล้ว)
- ใน `detector.py` กล้องอยู่ที่ 640x480 — ถ้าใช้แนวทาง headless ให้ **ลดเป็น 320x240** ที่ต้นทาง (หรือ resize ก่อนส่งเข้า Face Mesh)
- ลด **min_detection_confidence / min_tracking_confidence** เล็กน้อยถ้าต้องการ (เช่น 0.4) อาจช่วยในแสงน้อย แต่ไม่ควรลดมากเกินไป

---

## สิ่งที่ควรทำร่วมกัน (ไม่ว่าจะเลือกแนวทางไหน)

1. **ใช้ความละเอียดต่ำสำหรับ Detection:** 320x240 (หรือ 320x180) ก่อนส่งเข้า MediaPipe
2. **จำกัด FPS การตรวจจับ:** 5–10 FPS เพียงพอสำหรับการนับ “ง่วงต่อเนื่อง” และหาว และช่วยให้ Pi รันได้สมูธ
3. **refine_landmarks=False** ในทุกที่ที่ใช้ Face Mesh สำหรับโปรเจกต์นี้
4. **ปรับ EYE_AR_CONSEC_FRAMES ตาม FPS:** ถ้าใช้ 5 FPS แล้วยังใช้ 20 เฟรม = 4 วินาที; ถ้าใช้ 10 FPS, 20 เฟรม = 2 วินาที — อาจลดเป็น 10–15 เฟรมที่ 5 FPS เพื่อให้การแจ้งเตือนไม่ช้าเกินไป

---

## สรุปคำแนะนำสำหรับเคสของคุณ

- **ไม่สนใจการแสดงวิดีโอ แต่สนใจ detection + เสียง + ส่งเว็บ:**  
  → ใช้ **แนวทางที่ 1 (Headless)** ร่วมกับ **แนวทางที่ 3 (แยก thread detection)**  
  → Detection รันที่ 5–10 FPS, ความละเอียด 320x240, ไม่มี ImageTk/video Label  
  → GUI แสดงแค่สถานะและตัวเลข; เสียงและ backend ใช้ค่าจาก detection เหมือนเดิม

- **ถ้าอยากเห็นภาพบ้าง:**  
  → ใช้แนวทางที่ 2 + 3: แสดงภาพขนาดเล็กและข้ามเฟรม และให้ detection รันในอีก thread ที่ความละเอียดต่ำ

ถ้าต้องการ ผมสามารถเสนอ **ขั้นตอนแก้โค้ดเป็นจุดๆ** (เช่น แก้ `gui_update.py` / `detector.py` อย่างไร, เพิ่ม headless mode อย่างไร) ให้ตรงกับแนวทางที่คุณเลือกได้ต่อเลย
